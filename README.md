# Цифровой волонтёр Обнинска

Учебный сервис команды **team_escape** для учёта волонтёрской активности, подтверждения часов и обмена койнов на демонстрационные поощрения. Проект разработан для кейса № 02 направления «Городская среда».

Волонтёр регистрируется, выбирает мероприятие с понятной ставкой, участвует и отправляет отчёт. Координатор проверяет часы, при необходимости учитывает форс-мажор коэффициентом и подтверждает начисление. Каждая операция сохраняется с основанием.

## Технологии

| Часть проекта | Технологии |
|---|---|
| Основной frontend команды | **React + Tailwind CSS** |
| Backend | **Python 3.12+ и Django 6.0.9** |
| База данных для демонстрации | **SQLite** |
| Панель координатора и организатора | **Django Admin** |
| Обмен данными с React | **JSON API**, сессии Django, CSRF |
| Проверки | Django TestCase / TransactionTestCase, отдельные соединения SQLite для конкурентных операций |

Эта backend-ветка содержит API и дополнительные Django-страницы регистрации и личного кабинета, чтобы весь сценарий можно было проверить до подключения React-клиента. Они используют CSS из `static/css/`. Исходники и сборка React/Tailwind поддерживаются фронтенд-частью команды; в этой ветке нет `package.json` и команды запуска React.

## Роли и возможности

**Волонтёр:**

- регистрация и вход;
- каталог мероприятий со ставкой в койнах за час;
- запись на мероприятие и сохранение ставки на момент записи;
- форма отчёта после окончания мероприятия: часы и описание выполненной работы;
- просмотр статуса отчёта, причины отказа, подтверждённых часов и баланса;
- история начислений и списаний;
- запрос учебного поощрения через API магазина.

**Организатор / координатор:**

- создание мероприятий, настройка дат, места, описания и ставки;
- открытие и закрытие записи;
- просмотр отчётов, подтверждение фактических часов или отказ с объяснением;
- установка коэффициента при подтверждении — по умолчанию **1×**;
- контроль истории операций и запросов на условную выдачу поощрений.

## Как начисляются койны

```text
Койны = подтверждённые часы × ставка при записи × коэффициент
```

Например, **3 часа × 20 койнов/час × 1.5 = 90 койнов**. Коэффициент 1.5 можно указать при работе под дождём; причина сохраняется вместе с решением. При коэффициенте 1 стандартное мероприятие со ставкой 10 даёт 30 койнов за 3 часа.

- Ставка мероприятия — целое число от 1 до 100 000 койнов в час. Организатор задаёт её в админке.
- При записи ставка копируется в участие. Её последующее изменение влияет на новые записи, а старые сохраняют свои условия.
- Часы — от 0.1 до 24 с шагом 0.1.
- Коэффициент — от 0.10 до 10.00 с шагом 0.01. Любое отличие от 1 требует комментария.
- Результат округляется до целого койна по правилу **ROUND_HALF_UP**: 1.5 → 2. Расчёты используют Decimal.
- Нельзя подтвердить результат, округляющийся до нуля.

Запись и отправка отчёта сами по себе ничего не начисляют. Коэффициент, ставку и итог волонтёр задать не может.

## Сценарий участия

```text
Запись → registered → отчёт после мероприятия → pending → approved или rejected
```

В состоянии `registered` координатор ещё не может начислить койны. После отправки формы отчёт переходит в `pending`, и волонтёр может уточнять его до проверки. Подтверждённый или отклонённый отчёт окончателен: повторная отправка и повторное начисление запрещены.

Отчёт доступен после `ends_at`. Для совместимости со старыми событиями без даты окончания используется `starts_at`; организатору рекомендуется заполнять обе даты.

## Локальный запуск

Из корня репозитория, рядом с `requirements.txt`:

```bash
python -m venv .venv
```

Активировать окружение:

```powershell
# Windows PowerShell
.venv\Scripts\Activate.ps1
```

```bash
# Linux / macOS
source .venv/bin/activate
```

Установить зависимости и запустить Django:

```bash
python -m pip install -r requirements.txt
cd Obninsk_Hakaton2
python manage.py migrate
python manage.py seed_demo
python manage.py runserver
```

| Страница | Адрес |
|---|---|
| Регистрация волонтёра | http://127.0.0.1:8000/accounts/register/ |
| Вход | http://127.0.0.1:8000/accounts/login/ |
| Мероприятия и личный кабинет | http://127.0.0.1:8000/accounts/profile/ |
| Панель координатора | http://127.0.0.1:8000/admin/ |
| Каталог мероприятий для React | http://127.0.0.1:8000/api/events/ |

После регистрации пользователь автоматически входит в систему и видит мероприятия, ставки, баланс и свои участия. Координатор после обычного входа направляется в админку.

## Учебные данные

| Роль | Логин | Пароль |
|---|---|---|
| Координатор | `coordinator` | `Demo-Obninsk-2026!` |
| Волонтёр | `volunteer` | `Demo-Obninsk-2026!` |

`seed_demo` создаёт три события со ставками **10, 15 и 20 койнов/час**, три поощрения и группу «Координаторы». Новые учебные события уже закончились, чтобы отчёт можно было проверить сразу.

Повторный запуск не сбрасывает балансы, пароли, существующие даты или ставки. Если события были созданы предыдущей версией, установите ставки и прошедшее время окончания вручную в админке. Учебный аккаунт координатора не имеет прав суперпользователя. Для управления пользователями и правами: `python manage.py createsuperuser`.

## Проверка вдвоём на одном компьютере

1. В обычном окне зарегистрировать нового волонтёра.
2. Записаться на мероприятие с уже прошедшим временем окончания.
3. Отправить отчёт: 3 часа и описание работы. Проверить, что баланс пока равен нулю.
4. В инкогнито войти координатором в `/admin/`.
5. В разделе «Заявки и подтверждение часов» открыть «Проверить часы», подтвердить 3 часа и коэффициент 1.5, указав причину «Дождь».
6. Обновить кабинет волонтёра. При ставке 20 появится 90 койнов и запись с формулой.
7. Проверить, что повторное подтверждение не создаёт начисление.

## Обновление существующего проекта

Из папки с `manage.py`:

```bash
python manage.py migrate
python manage.py check
```

Миграция `catalog/0002_event_rates_and_reports.py` переносит старые участия: заявки без часов становятся записями, ранее отправленные часы остаются на проверке. Для старых подтверждений сохраняются ставка 10, коэффициент 1 и уже начисленная сумма. Балансы и история операций не пересчитываются и не начисляются повторно. Удалять базу или старые миграции не нужно.

## Тесты и демонстрация

```bash
python manage.py test accounts catalog --settings=Obninsk_Hakaton2.test_settings --noinput
python manage.py demo_scenario
```

Тесты покрывают регистрацию, каталог, отчёты, разные ставки, сохранение условий записи, коэффициенты, округление, проверку ролей, изоляцию данных, миграцию старого учёта, откат при ошибке и конкурентные операции.

`demo_scenario` создаёт отдельного учебного волонтёра и завершённое событие со ставкой 10: **3 часа → +30 → поощрение за 20 → остаток 10**, затем проверяет повторное начисление. Записи остаются видны в админке.

## API для React

Полный контракт и пример клиента: [docs/API.md](docs/API.md).

Регистрация: `POST /api/auth/register/`. Каталог со ставками: `GET /api/events/`. Запись: `POST /api/events/{id}/apply/`. Отчёт: `POST /api/activities/{id}/report/`. Решение координатора: `POST /api/coordinator/activities/{id}/review/`.

Авторизация основана на сессионных cookie. Перед POST нужно получить CSRF-токен; после входа или регистрации использовать новый токен из ответа. Для разработки React удобно настроить proxy `/api/` на Django, сохранив общий origin.

## Структура backend

```text
Obninsk_Hakaton2/
  accounts/                  — регистрация, профиль и страницы волонтёра
  catalog/models.py          — события, участия, отчёты, награды и операции
  catalog/services.py        — атомарная бизнес-логика начислений и покупок
  catalog/admin.py           — интерфейс организатора и координатора
  catalog/forms.py           — форма отчёта и форма решения
  catalog/views.py, urls.py  — JSON API для React
  catalog/migrations/        — схема и перенос существующих данных
  templates/                 — страницы для проверки backend
  static/css/                — стили Django-страниц
```

Основной баланс и подтверждённые часы хранятся в `accounts.VolunteerProfile`. Модель `Person` оставлена для совместимости регистрации; её старые поля не используются для начислений.

## Защита и границы демонстрации

Начисление, изменение часов/баланса и запись истории выполняются одной транзакцией. Списание защищено проверкой остатка в БД. Запись на событие и источник начисления уникальны. Историю и баланс нельзя вручную редактировать через админку. Координатору требуется отдельное разрешение; своё участие он подтвердить не может. В SQLite включён режим транзакций IMMEDIATE для сериализации конкурентных изменений.

Используются только учебные пользователи, события и поощрения. Койны не являются деньгами и не гарантируют настоящую награду. Реальная оплата, интеграции с городскими платформами и геолокация не подключены.

Настройки по умолчанию предназначены для локального запуска. Для развёртывания задаются `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=0`, `DJANGO_ALLOWED_HOSTS`; `.env` автоматически не загружается. Учебные аккаунты с общим паролем не подходят для публичного сервиса.
