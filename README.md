# Цифровой волонтёр Обнинска

Общее приложение команды **team_escape**: **React + Tailwind CSS** отображает интерфейс, **Python/Django** хранит пользователей, мероприятия, отчёты, часы, койны и запросы на поощрения.

Сценарий: регистрация → мероприятие → запись → отчёт → проверка координатором → начисление койнов → учебный обмен. Вся информация сохраняется в SQLite, а не в браузерном списке пользователей.

## Быстрый запуск на Windows

Нужны Python 3.12+ и Node.js 22.12+ из ветки 22.x либо Node.js 24.x. Сначала остановите старые серверы, занимающие порты 8000 и 5173.

1. Откройте корень проекта — папку с этим README.
2. Запустите **Start-Backend.cmd**. Он создаст `.venv`, установит Django, применит миграции, подготовит учебные данные и запустит backend.
3. Запустите **Start-Frontend.cmd**. Он установит frontend-зависимости из lock-файла и запустит Vite.
4. Оба окна оставьте открытыми.
5. Откройте **http://127.0.0.1:5173/** — это адрес общего приложения.

Вместо двойного щелчка можно выполнить в двух терминалах PowerShell из корня проекта:

```powershell
.\Start-Backend.cmd
```

```powershell
.\Start-Frontend.cmd
```

Скрипты не требуют активации PowerShell-окружения. Для первоначальной установки зависимостей нужен интернет. Работа самого учебного приложения использует локальные Django и SQLite.

## Что подключено

- Регистрация с проверкой пароля, логина, телефона и необязательных контактных данных.
- Вход, выход и восстановление сессии после обновления страницы.
- Каталог мероприятий из БД и запись без дубликатов.
- Отчёт после окончания мероприятия: часы и описание.
- Проверка отчётов в React-панели координатора и Django Admin.
- Коэффициент от **1.00 до 5.00**, шаг **0.05**, по умолчанию **1.00**. При отличии от 1 нужна причина.
- Создание мероприятий из React-панели; редактирование ставок и дат в Django Admin.
- Общий баланс, подтверждённые часы и история операций.
- Реальный каталог учебных поощрений, подтверждение обмена и запрос на выдачу.
- Отметка условной выдачи координатором.
- Серверные шаблоны мероприятий: создание, применение с новыми датами и архивирование.
- Отмена ожидающего выдачи поощрения волонтёром или координатором с однократным возвратом койнов.
- Состояния загрузки, ошибки, повтор запросов и адаптивное оформление.

Макетные цифры на главной заменены статистикой сервера. Баланс в шапке, профиле и обменнике берётся из одного источника.

## Начисление

```text
Койны = подтверждённые часы × ставка при записи × коэффициент
```

Примеры: **3 × 10 × 1.00 = 30**; **3 × 20 × 1.50 = 90**.

Расчёт выполняется на Django через Decimal с округлением ROUND_HALF_UP до целого койна. Ставка сохраняется при записи: изменение события не пересчитывает старые участия. Часы — 0.1–24 с шагом 0.1. Причина изменения коэффициента сохраняется вместе с решением.

Запись имеет статус `registered`. После отчёта — `pending`. Начисление происходит только при `approved`; отказ `rejected` требует причины. Пока отчёт не рассмотрен, волонтёр может его уточнить. Повторное подтверждение и изменение рассмотренного отчёта запрещены.

Форма открывается после `ends_at`; для прежних событий без окончания используется `starts_at`. `seed_demo` оставляет существующие события как есть, но при необходимости добавляет отдельное завершённое учебное событие для проверки отчётов.

## Обменник и единый баланс

Основной баланс — `accounts.VolunteerProfile.balance`. Все новые начисления и обмены проходят через `catalog/services.py`. Источник каждой операции связан с участием или запросом на поощрение.

Старые модели `shop.Profile`, `shop.Purchase`, `shop.Item` и `Person` сохранены. Старый независимый баланс не расходуется: `/shop/` ведёт в новый React-обменник. Архивные таблицы доступны суперпользователю только для просмотра. Новым пользователям больше не выдаются автоматические 100 монет старого обменника. Существующие архивные записи не удаляются и не добавляются к подтверждённому балансу.

Миграция переносит положительно оценённые позиции старого каталога в `catalog.Reward`. Для учебного обменника дополнительно создаются три стандартных поощрения.

Каждый запрос на обмен отправляет UUID намерения. При потере ответа клиент повторяет запрос с тем же UUID; повторное списание не происходит. Стоимость обмена берётся с сервера, а остаток проверяется в БД.

## Как проверить вдвоём на одном ПК

1. В обычном окне зарегистрировать волонтёра и записаться на завершённое событие со ставкой 10.
2. Отправить отчёт на 3 часа. Баланс должен остаться нулевым.
3. В инкогнито открыть тот же адрес `127.0.0.1:5173`, войти координатором.
4. В «Отчётах» подтвердить 3 часа при коэффициенте 1.00.
5. Вернуться в окно волонтёра и нажать «Обновить», если данные ещё не обновились. Баланс — 30.
6. В «Поощрениях» обменять 20 койнов на значок. Остаток — 10.
7. В окне координатора открыть «Выдача поощрений» и отметить запрос.
8. Проверить повторное подтверждение: backend вернёт конфликт без начисления.

Дополнительно создайте завершённое событие со ставкой 20 и подтвердите 3 часа с коэффициентом 1.50 и причиной «Дождь»: начисление 90 койнов.

## Обновление существующей базы

Миграции добавлены, база не включена в архив и не удаляется кодом. Существующие подтверждения, балансы и история сохраняются. Если раньше использовались миграции `catalog/0002_event_rates_and_reports` и `0003_multiplier_step`, их имена сохранены для совместимости.

Перед переносом в рабочий Git сохраните свои текущие изменения. Для первого запуска удобнее распаковать архив в отдельную папку и проверить на учебных данных. Для работы со своей базой перенесите изменения в существующую интеграционную ветку и выполните `migrate`; старые миграции удалять не нужно.

Все пользователи, события и награды учебные. Койны не являются деньгами и не гарантируют настоящую награду. ## Шаблоны и возвраты

Координатор сохраняет шаблоны на сервере и создаёт из них мероприятия с новыми датами. Из существующего мероприятия можно сохранить шаблон. Волонтёр и координатор могут отменить ожидающий выдачи запрос с однократным возвратом исходной цены; выданные запросы отменять нельзя. История сохраняет списание и возврат.

Шаблон содержит название, описание, место и ставку. При применении координатор задаёт даты и создаёт самостоятельное мероприятие. Архивирование шаблона не удаляет созданные события. Шаблоны первоначального браузерного макета автоматически не импортируются.

При отмене возвращается стоимость, зафиксированная при обмене, даже если каталог уже изменился. Исходное списание сохраняется, возврат записывается отдельной операцией. Повторная отмена не создаёт дополнительного возврата; выданный запрос отменить нельзя.

Установка обновления и перенос из ready-папки в репозиторий: [UPDATE-TEMPLATES-REFUNDS.md](UPDATE-TEMPLATES-REFUNDS.md).


## Как устроено приложение

| Компонент | Назначение |
|---|---|
| React + React Router | Страницы, формы, переходы, кабинеты двух ролей |
| Tailwind CSS | Оформление и адаптивная вёрстка |
| Vite | Запуск frontend и проксирование запросов `/api` в Django |
| Django | Регистрация, сессии, права, проверки, расчёт койнов, JSON API и Admin |
| SQLite | Пользователи, события, участия, шаблоны, запросы и история операций |

Браузер загружает React с порта 5173. React отправляет запросы на `/api/...` того же адреса, Vite передаёт их Django на 8000. Django проверяет сессию, CSRF, права и данные, выполняет операцию в базе и возвращает JSON. Интерфейс показывает ответ сервера. Скрытие кнопки в интерфейсе не заменяет проверку прав на backend.

Для изменения баланса используются атомарные операции `catalog/services.py`, выражения обновления БД и ограничения моделей. Подтверждение часов, обмен, выдача и возврат проверяют текущий статус. Если операция не проходит проверку, её изменения не сохраняются.

Код хранится в Git. Состояние SQLite — локально в `Obninsk_Hakaton2/db.sqlite3`. Поэтому другой компьютер после клонирования получает код, а пользователей и учебные данные создаёт при первом запуске. Два браузера, подключённые к одному запущенному backend, работают с одной базой.

## Доступ с телефона в одной сети

1. ПК и телефон подключите к одной локальной сети.
2. Backend оставьте на `127.0.0.1:8000`: запросы к нему передаёт Vite.
3. Из `FRONTEND/my-volunteer-app` запустите `npm run dev -- --host 0.0.0.0`.
4. В `Obninsk_Hakaton2/Obninsk_Hakaton2/settings.py` добавьте IP ПК в `ALLOWED_HOSTS` и frontend-origin в `CSRF_TRUSTED_ORIGINS`. Например, если IP ПК `192.168.1.162`:

```python
ALLOWED_HOSTS = ["localhost", "127.0.0.1", "192.168.1.162"]
CSRF_TRUSTED_ORIGINS = [
    "http://localhost:5173",
    "http://127.0.0.1:5173",
    "http://192.168.1.162:5173",
]
```

5. Перезапустите backend. Разрешите Node.js в брандмауэре для вашей частной сети.
6. Откройте на телефоне `http://192.168.1.162:5173` со своим IP из строки Network. Не используйте localhost на телефоне.

`DisallowedHost` / HTTP 400 в Django означает, что адрес не разрешён. HTTP 403 с `csrf_failed` требует проверить origin и обновить страницу. Если страница вообще не загружается, проверяйте Wi-Fi, VPN и брандмауэр. При смене IP обновите настройки.

## Pull Request в main

Сначала сохраните файлы коммитом и отправьте рабочую ветку. Пример для `integration/ready-polish`:

```powershell
git status
git add --all
git diff --cached --stat
git diff --cached --name-only
# Проверьте, что в индексе нет базы, .env, зависимостей и секретов.
git commit -m "Document integrated volunteer application"
git push -u origin integration/ready-polish
```

Команду push выполняйте для своей фактической ветки (`git branch --show-current`). Если изменений нет, новый коммит не нужен. Если README добавляется после открытия PR, обычный push в ту же ветку обновит PR автоматически.

1. Откройте репозиторий на GitHub.
2. Выберите вкладку **Pull requests → New pull request** (или **Compare & pull request** после push).
3. Установите **base: main**, **compare: integration/ready-polish**.
4. Посмотрите **Files changed**, добавьте понятный заголовок и описание поведения/проверок.
5. Нажмите **Create pull request**, попросите друга проверить изменения.
6. После успешных проверок и устранения конфликтов нажмите **Merge pull request → Confirm merge**. Если предлагаются разные способы и команда не выбрала иной, обычный merge сохраняет коммиты ветки и упрощает проверку слитых веток.

На ПК после слияния, при чистой рабочей папке:

```powershell
git switch main
git pull --ff-only origin main
```

Затем запускайте оба `.cmd`, как описано выше. GitHub сам Django и Vite не запускает; для сайта с постоянным публичным адресом нужен отдельный хостинг.

## Сохранить рабочую версию перед следующими изменениями

После проверки и слияния текущего результата в main:

```powershell
git switch main
git pull --ff-only origin main
git status
```

Убедитесь, что нет незакоммиченных изменений, и поставьте метку:


Метка навсегда указывает на выбранный коммит, пока её явно не переместили или удалили. Не перезаписывайте её: для следующего результата используйте `stable-demo-v2`.

```powershell
New-Item -ItemType Directory -Force ..\Obninsk-backups

```

Сохраните также локальные настройки и .env, если используете их, вне Git. Новые улучшения делайте в новой ветке:

```powershell
git switch -c feature/next-improvements
```

Коммитьте небольшие завершённые изменения. Не делайте экспериментальные изменения прямо в main.

## Вернуться к проверенной версии

Самый простой вариант — открыть сохранённую версию отдельно, сохранив текущую работу:

```powershell
git fetch origin --tags
git worktree add --detach ..\Obninsk-stable stable-demo-v1
```

Это создаст соседнюю папку с кодом из метки, не переключая текущую ветку. Для повторного просмотра используйте существующую папку, а не запускайте команду второй раз с тем же путём.

Чтобы восстановить и данные той версии, при остановленном backend скопируйте резервную базу:

```powershell
Copy-Item ..\Obninsk-backups\db-stable-demo-v1.sqlite3 ..\Obninsk-stable\Obninsk_Hakaton2\db.sqlite3
```

В `Obninsk-stable` запустите оба `.cmd`. Сначала остановите серверы другой версии, чтобы освободить порты. При необходимости настройте доступ с телефона. Код из метки со свежей базой от будущей версии может быть несовместим, поэтому копия базы нужна отдельно.

Если плохие изменения уже попали в общий main, используйте Pull Request с `git revert`, а не force push:

```powershell
git switch main
git pull --ff-only origin main
git switch -c fix/revert-bad-change
git log --oneline -10
# Для обычного коммита или squash-коммита:
git revert <bad_commit_sha>
# Для merge-коммита PR, вместо предыдущей команды:
# git revert -m 1 <bad_merge_sha>
git push -u origin fix/revert-bad-change
```

Замените `<...>` настоящим SHA и выберите один подходящий вариант. Revert отменяет конкретный коммит, а не автоматически всё после stable-demo-v1. При нескольких изменениях и миграциях откат планируется отдельно: revert кода не восстанавливает данные SQLite. Не удаляйте применённые миграции и не запускайте `git reset --hard` как универсальный способ ремонта.

## Очистка веток

После слияния, проверки main и сохранения метки:

```powershell
git fetch origin --prune
git branch --merged main
git branch -r --merged origin/main
```

Удаляйте только ненужные проверенные ветки, согласовав с другом. Пример:

```powershell
git branch -d integration/ready-polish
git push origin --delete integration/ready-polish
```

Не удаляйте main и ветки с несохранённой работой. Если `-d` отказывается, сначала выясните причину; после squash Git может не считать исходные коммиты слитыми. Резервные ветки можно оставить до окончания проекта.


## Где менять коэффициент

Для отдельного отчёта код менять не нужно. В React-панели координатора откройте «Отчёты», выберите ожидающий проверки отчёт, укажите коэффициент и причину, затем сохраните решение. В Django Admin аналогичные поля находятся в форме проверки участия. Значение по умолчанию — 1.00, диапазон — 1.00–10.00 с шагом 0.05. Пример: 3 часа × 10 койнов/час × 1.50 = 45 койнов. Коэффициент относится к конкретному подтверждению, а не ко всем действиям координатора.

Если нужно изменить правила в исходниках, они представлены в нескольких местах:

| Файл относительно корня проекта | Что менять согласованно |
|---|---|
| `FRONTEND/my-volunteer-app/src/CoordinatorDashboard.jsx` | Начальное состояние `coefficient`, HTML-поля min/max/step |
| `Obninsk_Hakaton2/catalog/services.py` | `validate_multiplier`, серверный диапазон и шаг; значения по умолчанию в `review_activity` |
| `Obninsk_Hakaton2/catalog/forms.py` | `ReviewForm.multiplier`: min_value, max_value, step_size, initial, widget и запасное значение в clean |
| `Obninsk_Hakaton2/catalog/models.py` | `Activity.multiplier`: default, validators и ограничения модели/БД |
| `Obninsk_Hakaton2/catalog/views.py` | Запасное значение коэффициента в endpoint проверки, если клиент его не прислал |

При изменении поля или ограничений модели создайте и примените новую миграцию, затем проверьте backend-тесты и frontend-сборку. Старые миграции не редактируйте:

```powershell
.\.venv\Scripts\python.exe .\Obninsk_Hakaton2\manage.py makemigrations catalog
.\.venv\Scripts\python.exe .\Obninsk_Hakaton2\manage.py migrate
.\.venv\Scripts\python.exe .\Obninsk_Hakaton2\manage.py test accounts catalog shop --settings=Obninsk_Hakaton2.test_settings --noinput
```

У старого ограничения БД исторически осталась нижняя граница 0.10 для совместимости существующих записей. Текущие формы, валидаторы и сервис разрешают новые решения только от 1.00. Не ориентируйтесь только на одну строку ограничения БД. Изменение правил не должно пересчитывать уже подтверждённые участия.

## Ручная проверка ветки перед Merge

Pull Request можно открыть до проверки: это предложение изменений, оно ещё не меняет main. Проверяйте именно отправленную compare-ветку, а не другую распакованную папку. На ПК друга при чистой рабочей папке:

```powershell
git fetch origin
git switch --track origin/integration/ready-polish
```

Если локальная ветка уже существует, вместо второй команды:

```powershell
git switch integration/ready-polish
git pull --ff-only origin integration/ready-polish
```

Используйте фактическое имя compare-ветки. Чтобы сверить версии, оба выполните `git rev-parse HEAD` и сравните результат с последним коммитом ветки в PR. Не переключайте ветку поверх несохранённой работы. Запустите backend и frontend из этой Git-папки; серверы из ready-папки остановите.

Проверка вдвоём может проходить на одном ПК: волонтёр в обычном окне, координатор в приватном. Телефон может подключиться к тому же backend по локальной сети. Отдельно запущенные копии на двух ПК используют разные базы и не показывают друг другу действия.

1. Зарегистрировать нового волонтёра: баланс 0, каталог и ставки видны.
2. Выбрать завершённое мероприятие со ставкой 10, записаться, отправить отчёт на 3 часа. До подтверждения баланс 0.
3. Координатор подтверждает при 1.00. Волонтёр видит 3 часа и +30 в истории.
4. Обменять 20 койнов на учебное поощрение: баланс 10, у координатора запрос на выдачу.
5. До выдачи отменить запрос: баланс снова 30, в истории исходное списание и возврат. Повторная отмена не должна увеличивать баланс.
6. Создать новый запрос, отметить выдачу координатором. Возможность отмены должна исчезнуть; сервер также запрещает отмену.
7. Создать шаблон, обновить страницу, создать по нему событие с новыми датами. Волонтёр видит событие с нужной ставкой.
8. На другом отчёте проверить коэффициент 1.50 с причиной: при 3 часах и ставке 10 начисляется 45. Отдельно проверить отклонение отчёта без начисления.
9. Проверить выход/вход и сохранение данных. Обычный волонтёр не должен получать доступ координатора.
10. Запустить backend-тесты, `npm run lint` и `npm run build`.

Повторное подтверждение, параллельные операции, запрет чужого возврата и защиту баланса проверяют автоматические backend-тесты. Если проверки прошли и друг просмотрел Files changed, можно выполнять Merge. Если нашли ошибку, исправляйте в той же ветке и делайте push: PR обновится автоматически.
