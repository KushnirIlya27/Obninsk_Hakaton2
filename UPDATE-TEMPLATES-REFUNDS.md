# Обновление: шаблоны мероприятий и возврат койнов

Это обновление для ранее выданного объединённого проекта React + Django.

## Установка на работающий проект

1. Остановите оба сервера. Скопируйте папку Obninsk_Hakaton2_ready целиком в резервную копию.
2. Распакуйте содержимое этого архива в Obninsk_Hakaton2_ready, согласившись заменить одноимённые файлы. Папки FRONTEND и Obninsk_Hakaton2 должны объединиться с существующими, а не оказаться во вложенной папке обновления.
3. Запустите Start-Backend.cmd. Он сам применит новую миграцию. Не удаляйте db.sqlite3, старые миграции и .venv.
4. Запустите frontend прежним способом. Для доступа с телефона: из FRONTEND/my-volunteer-app выполните `npm run dev -- --host 0.0.0.0`.
5. Обновите страницу браузера. Настройки settings.py, в том числе ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS, архив не заменяет. База и существующие балансы сохраняются.

## Что проверить

Координатор: рядом с «Мероприятия» есть «Шаблоны». Сохраните название, место, описание и ставку. Нажмите «Создать по шаблону», задайте даты, создайте мероприятие. Шаблон доступен после перезагрузки и на других устройствах. Из списка мероприятий также можно нажать «Сохранить как шаблон». Удаление из списка шаблонов не удаляет мероприятия.

Волонтёр: обменяйте 20 койнов на поощрение, в «Мои запросы на выдачу» нажмите «Отменить и вернуть койны». Баланс восстанавливается. В истории остаются исходное списание и отдельный возврат. Координатор может отменить запрос в «Выдача поощрений» или действием Django Admin. Повторная отмена не добавляет койны. Выданное поощрение отменить нельзя.

Архив не восстанавливает старые шаблоны, которые хранились только в localStorage первоначального прототипа: сохраните их заново. Новые шаблоны хранятся на сервере.

## Как загрузить на GitHub

Рабочая ready-папка — проверенная копия, а исходная Obninsk_Hakaton2 содержит историю Git. Сначала сделайте резервную копию обеих папок в проводнике. Команды ниже выполняются из PowerShell. Сохраните чужие незавершённые изменения отдельно, если они есть: при копировании одноимённые исходники заменяются проверенной ready-версией.

Откройте исходный репозиторий:

```powershell
cd 'C:\Users\Администратор\Desktop\vibes\hack\Obninsk_Hakaton2'
git status
git switch -c integration/ready-polish
```

Если git status показывает незавершённое слияние, сначала разберите его; следующие команды предназначены для обычной рабочей ветки. Если новая ветка уже существует, используйте другое свободное имя.

Скопируйте ready-проект в исходный репозиторий, сохранив историю Git и локальную базу:

```powershell
robocopy ..\Obninsk_Hakaton2_ready . /E /XD .git .venv venv node_modules dist .idea .vscode __pycache__ test-results playwright-report /XF *.sqlite3 *.sqlite3-* .env .env.* *.log *.zip *.patch
```

Используйте именно `/E`. Команда не удаляет файлы назначения. У robocopy код завершения 1 часто означает успешное копирование; смотрите сводку Failed/«Сбой».

Проверьте перенесённую копию из корня исходного репозитория (если здесь нет .venv, сначала запустите Start-Backend.cmd для её создания, затем остановите сервер):

```powershell
.\.venv\Scripts\python.exe .\Obninsk_Hakaton2\manage.py migrate
.\.venv\Scripts\python.exe .\Obninsk_Hakaton2\manage.py test accounts catalog shop --settings=Obninsk_Hakaton2.test_settings --noinput
Push-Location .\FRONTEND\my-volunteer-app
npm ci
npm run lint
npm run build
Pop-Location
```

Затем подготовьте коммит и посмотрите, какие файлы попадут на GitHub:

```powershell
git add --all
git diff --cached --stat
git diff --cached --name-only
git diff --cached
```

В коммите должны быть исходники, package-lock.json и новая миграция catalog/0004_eventtemplate_and_more.py. Не должно быть .venv, node_modules, базы, .env или паролей. .gitignore из обновления исключает локальные данные, но уже отслеживаемые Git файлы автоматически не перестают отслеживаться. Если в списке есть лишнее, снимите его с индекса командой `git restore --staged -- путь_к_файлу` и разберитесь до коммита.

Когда всё проверено:

```powershell
git commit -m "Integrate frontend and backend; add event templates and reward refunds"
git push -u origin integration/ready-polish
```

На GitHub откройте Pull Request: base `main`, compare `integration/ready-polish`. Дайте другу посмотреть изменения и проверьте общий сценарий. После этого слейте PR. При конфликтах не выбирайте вслепую целиком ours/theirs, особенно для accounts/models.py, urls.py и settings.py. Обычный push ветки не изменяет main. Force push здесь не нужен.

## Как убрать старые ветки

Чистите после слияния и проверки main. Сначала убедитесь, что рабочая папка чистая (`git status`), а друг сохранил свою работу. Не удаляйте main, frontend или backend, если там есть ещё не перенесённые изменения.

```powershell
git switch main
git pull --ff-only origin main
git fetch origin --prune
git branch --merged main
git branch -r --merged origin/main
```

Списки показывают ветки, чьи коммиты уже входят в main. Конкретную ненужную локальную ветку удаляйте так:

```powershell
git branch -d integration/ready-polish
```

Удалённую ветку (после согласования с другом):

```powershell
git push origin --delete integration/ready-polish
git fetch origin --prune
```

Имена — пример: удаляйте только проверенные ветки. `-d` защищает от удаления неслитых коммитов. Если PR слили через Squash, Git может считать ветку неслитой — сначала сравните изменения на GitHub, не заменяйте команду автоматически на `-D`. Резервные ветки пока оставьте. Для истории перед чисткой можно создать автономный архив:

```powershell
git bundle create ..\Obninsk-before-cleanup.bundle --all
```

Bundle сохраняет Git-коммиты и ссылки, но не незакоммиченные и неотслеживаемые файлы; для них нужна резервная копия папки.
